// what it's for

Stop hand-wiring model bindings

CortexJ is an AI runtime orchestration and model portability platform for the JVM. You write against one API — the platform decides where the model lives, which runtime serves it, and what to do when hardware or policy says no.

Model portability

One API for any compatible model — local, Hugging Face or plain HTTP repositories. Immutable revisions: what you resolved is what runs.

Runtime orchestration

The execution planner picks the best available runtime for each model and machine — deterministic scoring, hard constraints, fallback chains.

Java 8 → 25

Starters for every LTS line, identical business code. A starter built for a newer JVM fails fast with the exact remediation.

Explainable decisions

Every plan reports why: hard constraints considered, scores, memory estimates. No mystery paths, no provider-order luck.

Production-grade, not demo-grade

Lockfiles for reproducible plans, verified air-gap bundles, trust policies, checksum-verified downloads, typed errors with remediation. Built for audits, not demos.

Manage it without an IDE

A CLI covers the whole lifecycle: doctor checks the machine, plan predicts, pull downloads, run executes, server exposes an OpenAI-compatible API.

// faq

Frequently asked, honestly answered

Which Java versions are supported?

All LTS lines — Java 8, 11, 17, 21 and 25 — through dedicated starters. Business code is identical across them; a starter/JVM mismatch fails fast with an actionable diagnostic (CORTEXJ-CONF-0002).

Do I need Python?

No. CortexJ is JVM-only. For local GGUF text generation you point the llama.cpp provider at a llama-server binary; ONNX embeddings run on the bundled ONNX Runtime (CPU).

Is GPU supported?

Honestly: the llama.cpp provider plans GGUF for CPU and GPU; the bundled ONNX Runtime ships the CPU execution provider only. Hardware is probed, never assumed — unusable candidates are rejected with reasons in the plan, not at runtime.

Is this only an inference runtime?

CortexJ Runtime (inference) is the production product — but the platform tracks around it are shipped as incubating modules: interactive Lab, typed Data frames, reproducible Experiments, Training with LoRA and a Tensor/Autograd stack. The Runtime never depends on them; they feed into it.

How is this different from Spring AI or LangChain4j?

Those are application frameworks; CortexJ is the runtime layer underneath. It resolves models, plans execution and manages runtimes — and ships adapters that expose CortexJ models as Spring AI / LangChain4j ChatModel, StreamingChatModel and EmbeddingModel implementations, so your framework-side code stays unchanged.

When will it be on Maven Central?

Before a public 1.0: Maven Central publishing, the API stability freeze process and a signed-off production security review are the remaining gates. Until then the platform is 0.1.0-SNAPSHOT, documented exactly as it exists.
